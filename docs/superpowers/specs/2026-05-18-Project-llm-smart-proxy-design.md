# Project LLM Smart Proxy Design

Date: 2026-05-18

## Goal

Build **Project LLM Smart Proxy** from the existing Bogdan's LLM Smart Proxy codebase. The proxy remains OpenAI-compatible at the client edge and routes to exactly three upstream provider families: Windsurf, Claude, and Codex. Each family can expose multiple models through discovery and participates in the same scoring, fallback, health, and statistics flow.

## Scope

The implementation keeps the current Node.js proxy architecture, Docker-first local runtime, provider scoring, context handling, request transformation, streaming support, and health/model endpoints. It removes unrelated API-key providers from runtime configuration and setup, but does not remove discovery as a capability. Discovery becomes scoped to the supported provider families.

The proxy is intended to run locally with Docker Compose. Host-side authentication is acceptable and preferred for subscription/OAuth-backed providers.

## Supported Provider Families

### Windsurf

Windsurf is an upstream family with multiple SWE models. Authentication happens on the host through a browser login that produces a reusable `WINDSURF_API_KEY`. The implementation can reuse the known Windsurf cloud flow: browser one-time token registration, then HTTP/2 cloud chat transport to `server.codeium.com`.

The proxy exposes discovered Windsurf models as OpenAI-compatible model ids such as `windsurf/swe-1.6-fast`, `windsurf/swe-1.6`, `windsurf/swe-1.5-fast`, plus any future models returned by provider discovery.

### Claude

Claude is an upstream family backed by Anthropic/Claude subscription or Console access. Authentication is performed on the host, not reimplemented in the proxy. The setup flow instructs the user to run `claude setup-token` and place the resulting token in `.env` as `CLAUDE_CODE_OAUTH_TOKEN`.

The proxy uses that token when talking to Anthropic-compatible Claude endpoints. If a standard Console API key is also provided later, the design can support it through `ANTHROPIC_API_KEY`, but the primary mode for this project is the host-generated Claude Code OAuth token.

Relevant current behavior from Claude documentation:

- Claude Code can generate a long-lived OAuth token for environments where browser login is not available.
- Claude API requests require either `x-api-key` or `Authorization: Bearer <token>`, plus `anthropic-version`.
- Claude gateway support uses Anthropic Messages style endpoints for Claude Code clients, but this project exposes OpenAI-compatible endpoints to local clients and treats Claude as an upstream.

### Codex

Codex remains backed by the existing OpenAI/Codex OAuth proxy flow. Authentication happens on the host with Codex login, then `~/.codex/auth.json` is copied or mounted into `data/codex-auth.json`. The Docker Compose service runs the Codex OAuth proxy and the main proxy routes to it internally.

Codex models remain discoverable through the local Codex proxy `/v1/models` endpoint and appear under ids such as `codex/gpt-5.5`, `codex/gpt-5.4`, `codex/gpt-5.4-mini`, `codex/gpt-5.3-codex`, and `codex/gpt-5.2`, subject to what the local proxy exposes.

## External API

The external client API stays OpenAI-compatible:

- `POST /v1/chat/completions`
- `GET /v1/models`
- `GET /v1/capabilities`
- `GET /health`
- `GET /scores`
- `GET /discovery`
- `GET /stats`

Clients use `http://localhost:18900/v1` and any non-empty API key such as `proxy`, unless local auth enforcement is added later.

The `model` field accepts:

- Smart groups: `auto`, `auto-coding`, `auto-thinking`, `auto-tools`, `auto-text`, `auto-max`.
- Provider-prefixed ids: `windsurf/...`, `claude/...`, `codex/...`.
- Existing provider names generated by discovery, for direct routing and debugging.

## Discovery

Discovery remains a first-class feature but is limited to the three provider families:

- Windsurf discovery reads the local known model set, then refreshes from Windsurf cloud model metadata when `WINDSURF_API_KEY` is available.
- Claude discovery calls the Claude models endpoint when `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` is available. If the call fails, bundled Claude seed models are used.
- Codex discovery calls the local Codex proxy `/v1/models` endpoint when `ENABLE_CODEX=true` and the Codex proxy is running. If unavailable, bundled Codex seed models are used.

Discovery writes `/data/providers.json`, preserving the current hot-reload behavior. The seed file becomes a small fallback definition for the three provider families rather than a catalog of unrelated public providers.

## Routing And Scoring

The routing layer keeps the current provider scoring model:

- Prefer healthy providers with good latency and success rate.
- Use capability matching for smart groups.
- Preserve session affinity when a provider works for the current conversation.
- Respect cooldowns, quota failures, and learned compatibility flags.
- Fail over within the three supported families before returning an error.

The benchmark/model scoring table should be pruned to the supported model families only, while preserving frontier scoring for Claude, GPT/Codex, and Windsurf SWE models.

## Request Translation

The main proxy continues accepting OpenAI-compatible chat requests. Provider adapters translate as needed:

- Codex adapter: OpenAI-compatible request/response, mostly pass-through to the Codex local proxy.
- Windsurf adapter: OpenAI-compatible request converted to Windsurf cloud transport and back to OpenAI-compatible response/SSE.
- Claude adapter: OpenAI-compatible request converted to Anthropic Messages format and back to OpenAI-compatible response/SSE.

Tool calling support should remain part of the contract where the upstream supports it. Existing tool-message cleanup, orphaned tool-call stripping, `stream_options` cleanup, and context compaction remain useful and should be kept.

## Docker Runtime

Docker Compose should start:

- `llm-proxy`: the main Project proxy on `18900`.
- `llm-discovery`: the scoped discovery worker.
- `codex-proxy`: enabled when `ENABLE_CODEX=true`, using `data/codex-auth.json`.

Claude and Windsurf do not need separate containers for auth. Their host-produced credentials are passed to the main proxy through `.env`.

MemPalace can remain optional. If kept enabled by default, documentation should describe it as optional local memory rather than a provider requirement.

## Setup Flow

`setup.sh` should become focused and short:

1. Create `.env` from `.env.example`.
2. Ask which provider families to enable: Windsurf, Claude, Codex.
3. For Windsurf, run or describe the host browser-auth flow and store `WINDSURF_API_KEY`.
4. For Claude, instruct `claude setup-token`, then ask the user to paste/store `CLAUDE_CODE_OAUTH_TOKEN`.
5. For Codex, run or describe `npx @openai/codex login`, then copy `~/.codex/auth.json` to `data/codex-auth.json`.
6. Start Docker Compose with the needed profiles.
7. Print health, models, and one test `curl`.

The generated `.env.example` should contain only variables relevant to these modes.

## Documentation

Rename all user-facing references from **Bogdan's LLM Smart Proxy** to **Project LLM Smart Proxy**.

Rewrite `README.md` and `INSTRUCTIONS.md` around:

- Supported provider families and auth modes.
- Local Docker setup.
- Model discovery behavior.
- OpenAI-compatible client setup for IDEs and agents.
- Troubleshooting for missing host credentials, expired tokens, unavailable Codex proxy, and provider discovery failures.

Remove long provider catalogs for unsupported upstreams.

## Testing

Add focused tests for behavior that can be verified without live credentials:

- Seed provider hydration includes only Windsurf, Claude, and Codex families.
- Discovery endpoint generation ignores unrelated providers.
- Provider model ids are namespaced consistently.
- OpenAI-to-Anthropic request conversion preserves messages, tools, max tokens, and streaming intent.
- Anthropic-to-OpenAI response conversion handles non-streaming and streaming output.
- Setup/docs variables match `.env.example`.

Live provider tests should be manual or opt-in because they require personal subscription tokens.

## Risks

Claude OAuth token behavior can change, so setup should prefer the official `claude setup-token` flow rather than a custom PKCE implementation.

Windsurf cloud transport is based on a reverse-engineered local-compatible flow. The adapter should fail clearly with setup guidance if the API key or cloud transport stops working.

Codex model availability depends on the installed `openai-oauth` proxy and the host's Codex login state. Health checks should distinguish "proxy down" from "auth missing" where possible.
